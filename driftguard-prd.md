# Product Requirements Document (PRD)
## Project Name: DriftGuard
### Production LLM-Output Semantic Drift & Reliability Monitor

---

## 1. Executive Summary & Market Problem

### 1.1 The Semantic Drift Bottleneck
Large Language Models (LLMs) deployed in production systems are highly dynamic, non-deterministic, and prone to silent failures. Over time, changes in user query distributions, updates to upstream base models, or shifts in context data lead to a degradation of output quality known as **semantic drift** [457]. 

Unlike traditional software services where failures are marked by clear HTTP 5xx codes, semantic drift is silent. An LLM might continue to return status `200 OK` while its outputs degrade into unhelpful, toxic, or flatly hallucinated responses [419]. 

Traditional observability platforms (e.g., Datadog, Prometheus) measure system throughput, memory, and network latency, but lack any awareness of linguistic or vector semantics. Specialized LLM-evaluation frameworks exist (e.g., LangSmith, Phoenix), but they either require expensive SaaS subscriptions, introduce severe latency bottlenecks by proxying synchronous API traffic [567], or are too monolithic to run cost-effectively at production scale.

### 1.2 The DriftGuard Solution
**DriftGuard** is an open-source, highly available, and lightweight self-hosted LLM reliability monitor designed to run natively on the **Zerops Developer-first Platform-as-a-Service (PaaS)** [370]. It decouples LLM observability into a high-throughput synchronous API and an asynchronous background evaluation queue [312].

By running its vector operations on **Qdrant** [371] and coordinating task execution via **Valkey** [371], DriftGuard computes semantic distance between real-time LLM outputs and a baseline of gold-standard responses [426]. Developers receive immediate notifications when system behavior drifts beyond defined thresholds, allowing teams to catch hallucinations, prompt injections, and regression bugs before they impact users.

## 2. Product Objectives & Target Audience

### 2.1 Core Value Propositions
*   **Decoupled High-Performance Observability:** Process thousands of logs per second with sub-millisecond API response latency, offloading heavy vector computations and LLM evaluations to isolated background workers [312].
*   **Infrastructure Parity & Security:** Ensure complete security by stashing production logs and embeddings within an isolated, private network topology, keeping sensitive customer telemetry entirely out of third-party SaaS platforms [373].
*   **Deep Infrastructure Observability:** Turn the "black-box" monitoring system into a highly observable asset. With the **Infrastructure Pulse** dashboard, team leads and hackathon judges can view live metrics from database connections, Valkey queues, and Qdrant cluster latencies [323].

### 2.2 Target Audience
*   **AI Platform Engineers / ML Devs:** Teams managing multiple LLM pipelines in production who require automated, cost-effective alerts on linguistic regressions.
*   **DevOps / SREs:** Engineers focused on maximum uptime, latency control, and container health, who value declarative infrastructure (`zerops.yaml`) and zero-downtime rolling deploys [110, 312].
*   **Developers Building with AI Agents:** Teams using agentic workspaces (such as the **Zerops Control Plane / ZCP**) who need persistent, codified system specifications to preserve context across multi-agent sessions [407, 805].

## 3. Product Capabilities & Functional Requirements

### 3.1 High-Throughput Ingestion Engine
*   **FR-1.1:** The ingestion backend MUST expose a lightweight, synchronous POST endpoint (`/api/v1/telemetry/log`) written in **FastAPI** [35, 337].
*   **FR-1.2:** This endpoint MUST validate the schema of the incoming payload, containing:
    *   `project_id` (UUID): The logical application being monitored.
    *   `prompt_text` (String): The input string sent to the production LLM.
    *   `response_text` (String): The output string generated by the production LLM.
    *   `timestamp` (ISO-8601 string): The exact execution time.
    *   `metadata` (JSON Object): Extensible fields (e.g., latency, model_name, user_id).
*   **FR-1.3:** Upon receiving a valid payload, the API MUST immediately write the raw record to the **PostgreSQL** database and append a task payload to the **Valkey** task list queue (`drift_eval_queue`) [23, 312].
*   **FR-1.4:** The API MUST return a `202 Accepted` status code with a unique telemetry transaction ID within **< 5ms** to avoid adding latency to the upstream application's execution loop.

### 3.2 Analytical Engine & Background Worker
*   **FR-2.1:** An isolated **Python Background Worker** service MUST run continuously, listening to the Valkey task list via blocking pop operations (`BLPOP`) to prevent polling overhead [23, 35].
*   **FR-2.2:** For each popped payload, the worker MUST:
    1.  Generate a **384-dimensional dense vector embedding** of the `response_text` using a local, highly efficient **`all-MiniLM-L6-v2`** Sentence-Transformers model [40, 56, 427].
    2.  Query the **Qdrant Vector Database** to compute the cosine similarity against the "gold-standard" baseline vectors configured for that project ID [42, 547].
    3.  Compute the **Semantic Drift Distance** using the formula:
        $$\text{Semantic Drift} = 1.0 - \text{Cosine Similarity}(\vec{v}_{\text{response}}, \vec{v}_{\text{baseline}})$$
    4.  Compare the drift value against the defined alerting thresholds stored in PostgreSQL [336].
    5.  Persist the final evaluation score, latency, and nearest-neighbor reference ID back to PostgreSQL [336].

### 3.3 Alerting & Threshold Routing Engine
*   **FR-3.1:** The alerting system MUST support three distinct alert routing types based on severity thresholds defined by the user:
    *   **INFO (Drift $> 0.15$):** Logs the event silently and updates the trend metrics. Used for minor language style changes.
    *   **WARNING (Drift $> 0.30$):** Packages a daily digest of drifted inputs and sends a consolidated summary email/webhook. Indicates a probable shift in user context.
    *   **CRITICAL (Drift $> 0.45$):** Triggers an immediate notification to connected webhooks (Slack, Discord, orPagerDuty). Indicates model collapse, severe prompt injection, or complete garbage output.
*   **FR-3.2:** To prevent alert fatigue, the background worker MUST implement an evaluation deduplication check in **Valkey** (using temporary Redis-style keys with a 60-second TTL), grouping duplicate alerts for identical failure modes [30].

### 3.4 Performance & Trend Analytics Dashboard (Frontend)
*   **FR-4.1:** A **Next.js** SPA frontend MUST display real-time metrics on a clean, modern user dashboard [8, 23].
*   **FR-4.2:** Key visualizations MUST include:
    *   **Drift Trend Line:** A time-series chart showing average semantic drift over time (hourly, daily, weekly) with highlighted alert threshold lines.
    *   **Scatter Plot:** An interactive 2D visualization of Qdrant vector coordinates to visually group clusters of shifted LLM responses.
    *   **Alert Feed:** A searchable, real-time list of warnings and critical alerts showing raw prompts, shifted responses, and nearest matching baseline answers.

### 3.5 Infrastructure Pulse Diagnostics Dashboard (The Observable Secret Weapon)
*   **FR-5.1:** The Next.js frontend MUST include a dedicated diagnostics view called the **"Infrastructure Pulse"** [7, 323].
*   **FR-5.2:** This view MUST poll a special backend endpoint (`/api/v1/diagnostics/health`) every 2,000ms [312].
*   **FR-5.3:** The page MUST visually showcase the distributed Zerops microservices architecture by rendering live system health metrics:
    *   **Valkey Queue Size:** The length of the Redis list (`LLEN drift_eval_queue`), proving async decoupling.
    *   **Qdrant Vector Cluster Latency:** Round-trip query times from the API to the private Qdrant instance.
    *   **PostgreSQL Connection Pool Status:** Number of active/idle database connections.
    *   **Worker Active State:** Running status and thread usage of the background Python containers.
    *   **Storage Metrics:** Total S3 bucket disk usage for archived logs in Zerops Object Storage.

The application is structured as a decoupled, 5-service distributed system connected entirely via secure, isolated private networking on Zerops:

```
                                          │
                                          ▼ (API Calls)

                                │          │         │
      ┌─────────────────────────┘          │         └─────────────────────────┐

      ▼                                    ▼                                   ▼
┌───────────┐                        ┌───────────┐                       ┌───────────┐

      │                                    │                                   │
      │ (Nearest-Neighbor Queries)         │ (Consumes Jobs via BLPOP)         │ (Saves Evaluations)

                                ┌──────────────────────────┐
                                │  Zerops Object Storage   │
                                └──────────────────────────┘
```

### 4.1 Zerops Service Network Topology (VXLAN)
DriftGuard relies on Zerops' dynamic dedicated infrastructure deployed with each project [373]:
*   **Isolated Private VXLAN Network:** Services communicate securely using Zerops' automatic internal hostname discovery [251, 373]. Hostnames like `postgres`, `valkey`, `qdrant`, `api`, and `worker` resolve directly on the private network [215, 252].
*   **Port Restriction (No Exposed Ports):** Databases (`postgres`), caches (`valkey`), and vector databases (`qdrant`) are configured with **zero public IP access** [220, 258]. The only entry point from the public internet is through the L7 Balancer pointing to the Next.js frontend and the FastAPI ingestion endpoints [220, 274].
*   **Secure Environment Referencing:** Database and database connection credentials are dynamically referenced using Zerops' cross-service variable inheritance (e.g., `${db_hostname}`), eliminating hardcoded secrets in the codebase [119, 122].

## 5. Non-Functional Requirements (NFR)

### 5.1 Scalability & Resource Allocation
*   **NFR-1.1 (Autoscaling):** FastAPI API and Python Worker runtimes MUST utilize Zerops' vertical and horizontal autoscaling properties [374].
    *   **FastAPI Ingestion Container:** Min Containers: 2, Max Containers: 6, RAM: 0.5 GB, CPU: Shared mode (scales dynamically to dedicated CPU under massive log volumes) [173, 374].
    *   **Background Python Worker Container:** RAM: 2.0 GB (configured to accommodate the local Sentence-Transformers model files loaded into RAM safely), Disk: 10 GB [35, 173].
*   **NFR-1.2 (Database HA Mode):** For production environments, the PostgreSQL database MUST be provisioned in High Availability (HA) mode with 3 replicas [173, 374].

### 5.2 Performance & Limits
*   **NFR-2.1:** Under sustained loads of **500 telemetry logs/sec**, the API response time MUST remain below **10ms**.
*   **NFR-2.2:** Background evaluations MUST complete vector calculations and write alert decisions within **500ms** of log ingestion.
*   **NFR-2.3:** Large telemetry data (such as extensive LLM conversation logs) uploaded in bulk MUST be capped at **50MB** per single HTTP request, aligned with the L7 Balancer upload limit [272].

### 5.3 Reliability, Health & Graceful Restarts
*   **NFR-3.1 (Zero-Downtime Rolling Deploys):** New deployment containers MUST start, pass readiness checks, and warm up local ML embedding models before old containers are terminated (`temporaryShutdown: false` in `zerops.yaml`) [379, 386].
*   **NFR-3.2 (Readiness Checks):** Runtimes MUST expose explicit `/status` or `/health` health-check endpoints returning HTTP 200, which are polled continuously by the Zerops balancer [379, 386].

## 6. Detailed Data Schemas

### 6.1 PostgreSQL Relational Database Schema

```sql
-- Projects metadata table
CREATE TABLE IF NOT EXISTS projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(255) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- LLM Telemetry logs & evaluation runs
CREATE TABLE IF NOT EXISTS telemetry_runs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    prompt_text TEXT NOT NULL,
    response_text TEXT NOT NULL,
    embedding_vector REAL[] NULL, -- Stored locally if required, otherwise queried on Qdrant
    drift_distance DOUBLE PRECISION NOT NULL DEFAULT 0.0,
    status VARCHAR(50) NOT NULL DEFAULT 'QUEUED', -- QUEUED, PROCESSING, EVALUATED, FAILED
    nearest_baseline_id UUID NULL,
    latency_ms INTEGER NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Alert configuration thresholds
CREATE TABLE IF NOT EXISTS alert_rules (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    metric_type VARCHAR(50) NOT NULL DEFAULT 'SEMANTIC_DRIFT',
    warning_threshold DOUBLE PRECISION NOT NULL DEFAULT 0.30,
    critical_threshold DOUBLE PRECISION NOT NULL DEFAULT 0.45,
    slack_webhook_url TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Log outbox table to guarantee reliable event-driven delivery (Outbox Pattern)
CREATE TABLE IF NOT EXISTS telemetry_outbox (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    run_id UUID REFERENCES telemetry_runs(id) ON DELETE CASCADE,
    payload JSONB NOT NULL,
    status VARCHAR(50) NOT NULL DEFAULT 'PENDING', -- PENDING, DISPATCHED, FAILED
    retry_count INT DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### 6.2 Qdrant Vector Collection Configuration
*   **Collection Name:** `drift_baselines_{project_id}` [259].
*   **Vector Configuration:**
    *   **Dimension Size:** 384 dimensions (for Sentence-Transformers model `all-MiniLM-L6-v2`) [40, 259, 336].
    *   **Distance Metric:** Cosine similarity [259, 336].
*   **Payload Layout:**
    ```json
    {
      "id": "uuid-v4-of-baseline",
      "vector": [0.035, -0.12, ..., 0.78],
      "payload": {
        "text": "The golden expected answer",
        "category": "security-protocols",
        "baseline_version": "v1.4"
      }
    }
    ```

## 7. Failure Modes & Mitigations Matrix

| Failure Mode | Root Cause | Detection Mechanism | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| **Worker OOM Crashes** [315] | Ingesting large raw text inputs leading to massive RAM usage during tokenization [315]. | Zerops Container Events show exit code `137` [44]. | Implement strict input text truncation (e.g., truncate text to 2048 characters max before tokenization) [315]. |
| **Qdrant Connection Timeout** [315] | Qdrant cold start or network jitter on private VXLAN [315]. | FastAPI logs `ConnectionError` on telemetry write. | Use Zerops `depends_on` in `zerops.yaml` to prevent startup race conditions; implement retry loop with exponential backoff on connection failure [43, 315]. |
| **Valkey Queue Bloat** [315] | Ingestion API outpaces Background Worker under heavy load spikes [315]. | Infrastructure Pulse shows `LLEN drift_eval_queue` exceeding threshold (e.g., > 10,000 items) [315]. | Configure Zerops horizontal autoscaling on Python Background Worker to spawn extra containers when queue length triggers high load metrics [173, 315]. |
| **Outbox Desync** [315] | Ingestion API writes run metadata to Postgres but fails to enqueue to Valkey. | Telemetry outbox records remain in `PENDING` state [315]. | Implement a lightweight cron job in FastAPI using Zerops crontab to poll for `PENDING` records in the `telemetry_outbox` table and safely re-queue them into Valkey [315, 383]. |
